## What was built

**One new endpoint (D1).** `GET /api/runs?limit=&prefix=` (`backend/app/api/runs.py`, declared before `/{correlation_id}` so the literal path wins): the latest runs across every claim, newest first by the `pipeline_started` row, each a `RunListItem` — the `RunSummary` fields plus `claim_id`, `claim_number`, `claimant_name` and `human_decision` (`runs/models.py`). `limit` 1–100 (default 20); `prefix` 8–36 characters of `[0-9a-fA-F-]`, lower-cased, anything else 422, narrows to the runs whose id starts with it (0, 1 or many), which is how the Audit page turns the eight-character id the pages show into a run. `RunsRepository.list_recent_runs(conn, limit, prefix)`: three reads — the starts joined to `claims`, the runs' rows through the existing `_summarise`, `AuditRepository.human_decisions` for the claims — and the prefix re-validated before it becomes a LIKE pattern, because a pattern is safe only while it can hold no metacharacter. No migration. Nothing existing changed.

**The Audit page** (`frontend/src/pages/AuditPage.tsx`, rewritten in eight parts, every function under 50 lines). The box reads *Run id* with the hint "Paste a run id, or its first eight characters."; `classifyRunId` (`pages/auditDerivation.ts`) sorts what was typed into a whole id (loaded at once), a prefix of eight or more characters (resolved through the endpoint: one match loads, none or several is said in a sentence), too few characters ("Give at least the first eight characters of the run id." — never sent), or characters a run id never has. The run is named as the run page names it, through the shared `components/ClaimLine.tsx` (moved out of `RunDetailPage`), then "Standard run · started 15 Nov 2026, 15:09:03 · Settled at $78,000 · Open the run page", the outcome through `claimCopy.runOutcome` so a decided run reads "Rejected after human review". One row per record: *When* with seconds (`formatDateTime(…, {seconds: true})`), *Who* in words (`rowAuthor`: Doc-Parser, Validator, Adjuster, Guardrail, Orchestrator, A person), *What happened* as one sentence (`rowSentence`: the run page's own sentences through the now-exported `describeRow`, `ruleLine`, `failureReason`, `runCopy.aborted`, `claimCopy.runOutcome`; new in `copy/audit.ts` only "Run started: Standard run", "No rule fired; the claim settles", "Sent to a person: …" and "Rejected by Dermot Copps"), *Record* ("#210 · a1b2c3d4e5f6", its ⓘ `tooltips.chainHash` in the Guide's words for the hash). *Verify chain* answers in a sentence: "Checked all 225 records in the ledger, this run’s included: every hash matches." or "A break at record 57: the record’s own hash does not match its contents." / "…the link to the record before it does not match." Unknown id, failed load (`ApiError` with the status, new in `api/client.ts`), empty and loading states in words; the waking notice stays; `?correlation_id=` stays in the address so every link in still lands.

**The record viewer.** `components/Dialog.tsx` (D2, hand-rolled because jsdom 29 cannot drive `showModal()`): labelled `role="dialog"`, focus on *Close* when it opens and back on the opener when it closes, Tab and Shift+Tab cycle inside it, Escape and the backdrop close it, the page's scroll locked, `max-h-[85vh]` and scrolling inside. `components/RecordTree.tsx` (D3): the record's keys and the level beneath open, deeper levels closed with "{n keys}" / "[n items]", kinds coloured, strings over 240 characters folded behind *Show all*, text wrapped and never wider than the dialog. `components/RecordView.tsx`: the tabs *Record* and *Instructions sent* (the second only when `extractPrompt`, moved from `AgentCard` (D8), finds `llm_call.prompt`), the headings *System instructions* and *Message to the model*, the fixture record's sentence "No model was called for this record: the Adjuster’s figure came from the fixed demonstration file.", and *Copy record* copying `JSON.stringify(entry, null, 2)` — the whole row as the API served it (D4). `components/RecordDialog.tsx` wraps the view in the dialog; the Audit page opens it from a row's sentence button and the row.

**The Guide and the links in.** *Try it* step 5 says *Verify chain* (D5); *Reading a run page* reworded; a new card *Reading the audit log* (O1); `docs/walkthrough.md`'s Audit section. *View audit log* on the run page and *Audit log* on the claim page's run lines were unchanged and land on the run they name (`?correlation_id=`).

## The four changes made during the verification (15 November, Dermot's request, frontend only, `5981af0`)

1. **Recent runs below the records**, so a visitor arriving from *View audit log* sees their run first; with no run loaded it follows the Run id box.
2. **Recent runs as a table in the Claims list's style:** Claimant with the claim number beneath in small grey monospace, Kind of run, Started, Outcome as a `StatusBadge` in the run page's colours and words (*Approved* / *Rejected* from `human_decision`); the claimant's name is the link that loads the run; heading "The 20 most recent runs".
3. **A `chunk_id` value in the tree is a link** to that passage on the Policy page (`/policy#<chunk_id>`); the record and *Copy record* unchanged.
4. **The run page's cards take up the viewer.** The dialog's body became `RecordView`, shared with the cards: an opened card shows the agent's record through the same parts in place of the old *prompt* / *System* / *User* panel and the dark `JsonBlock`; the fixture Adjuster says no model was called. How the card gets its record: live, from the audit row the run page already hands it, which the stream re-reads at every agent completion, with `runCopy.recordPending` ("Waiting for this agent to complete…") until it arrives; afterwards from the same query on load. The old panel's fallback — the raw prompt template fetched for rows older than the Phase 8.3 capture, with a caveat — went with it, and so did `useAgentPrompt` and `getAgentPrompt`, which had no other caller; the viewer shows no instructions tab for such a record, which is what the trail says. Nothing on the run page uses `JsonBlock` now; its one user is the Agents test bench's result panel.

## Findings and deviations from the plan

- **Two changes at the gate and four during the verification** (register R-27), all built as asked.
- **Three sentences beyond the plan's words:** "A run id is made of the characters 0–9, a–f and hyphens." for an id typed with other characters (so the eight-character sentence is not given for the wrong reason); "Recent runs could not be loaded." for the table's own failure; "Finding the run…" on the button while a prefix is being resolved.
- **`ApiError`** in the API client carries the status, so the page can tell "not found" from any other failure; every other caller still reads only the message.
- **The prompt-template fallback removed** (change 4, above): a quiet removal of code with no remaining caller, reversible, told to Dermot at the time.
- **The Adjuster above the reported amount, again:** run `f97e236e` recommended $920,000 on an $850,000 claim, as run `2bd08a61` recommended $950,000 the same day; added to the backlog's finding.
- **`RunFinder` is 49 lines**, a flat form; `Dialog` and `RunFinder` were each over 50 at first and were split (`useModalLifetime`, `handleKey`; `resolveShortId`).
- **Test counts against the plan:** backend 552 against "about 548", frontend 254 against "about 250", then 256.
- **The ruff formatter was not applied to existing lines:** it would have reformatted untouched code in `runs/repository.py` and `api/runs.py` (CI runs `ruff check`, not `ruff format`); the new code was written to its style by hand and `ruff check` is clean.
- **The Azure database** holds 33 claims and 33 runs at the close (31 claims on 14 November; Dermot's two Northwood claims of 15 November), 225 audit rows, chain `ok`.
