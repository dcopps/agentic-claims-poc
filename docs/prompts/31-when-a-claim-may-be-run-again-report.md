## What was built

**The rule.** A claim a person has approved or rejected is closed to further runs, on every route by which a run can start. The decision is read from the audit trail's `human_approval` / `human_rejection` rows, never from `claims.status`: a claim stored `aborted` by a rejection and a claim stored `settled` by an approval are refused for the same reason, by the same sentence, and a database restored from the trail alone would refuse the same claims.

**Backend** (`backend/app/`). `AuditRepository.human_decisions(conn, claim_ids)` — one grouped `SELECT DISTINCT ON (claim_id) … WHERE agent = 'human' AND step = ANY(…) ORDER BY claim_id, created_at DESC, audit_id DESC` over the existing `audit_log_claim_id_idx`; the latest row per claim wins; an empty input returns `{}` without a query; no migration (D6: one grouped function here, not Prompt 29 plan §4's per-claim `RunsRepository` function and its exception class). `ClaimRecord.human_decision: 'approved' | 'rejected' | None` (`claims/models.py`, default None), filled by `ClaimsRepository.get` and `list_claims` through `_with_decisions`, so every claim response carries it: `POST /api/claims` (always null), `GET /api/claims`, `GET /api/claims/{id}`, `POST /api/claims/{id}/human-decision`, the MCP `get_claim` and, with D1, the MCP `list_claims` item (`ClaimListItem`). `api/pipeline.py`: `_require_known_claim` now returns the record (the raw `_claim_exists` query is gone), `_require_open_claim(claim)` raises 409 with `closed_claim_detail(claim)` — "claim CLM-2026-2FFB0434 was approved by a person and is closed to further runs" — third in both endpoints, after the two 404s and before the prior-run and active-run 409s (D8: a decision is the permanent reason). `mcp/tools._prepare_scenario_claim` raises `ToolError("claim_closed: " + the same sentence)` after the tag check and before the in-flight check; the call is recorded in `mcp_tool_calls` with `outcome = 'error'` like the other refusals; the tool's description and `docs/demo-mcp.md` say a decided claim is refused. `pyproject.toml` and `uv.lock` `0.10.2`.

**Frontend** (`frontend/src/`). `api/types.ts`: `ClaimRecord.human_decision`, `HumanDecisionKind` moved here. `pages/ClaimsPage.tsx` split from one 75-line component into `ClaimsPage` (24 lines), `useRunTrigger`, `ClaimsTable` (which owns which row's confirmation is open, so opening another row's closes it), `ClaimRow`, `RowActions` and `ConfirmRerun`. The primary button reads *Process* for a claim with status `received` and *Run again* otherwise (`copy/claims.ts`, new). On a settled claim *Run again* opens an anchored panel, "This claim has already settled. Run it again?" with *Run again* and *Cancel* (D2), which closes on either button, on Escape, on a click anywhere outside it, or when another row opens its own; *Strict re-run* asks nothing (D3). A decided claim has both buttons disabled with the reason leading each tooltip: "Closed: a person approved this claim; it cannot be run again." / "Closed: a person rejected this claim; it cannot be run again." (`tooltips.disabledClosedApproved` / `disabledClosedRejected`). `REPLAYABLE` loses `aborted`, which could never enable the button now. The Decision card ends "The claim is closed to further runs." (`closed-to-runs`); the review panel's fourth sentence under the buttons reads "Either decision closes the claim to further runs." (O1); the Guide's `tryMore[0]` gains the clause.

## The two fixes (15 November 2026, from the verification, frontend only, no version change)

1. **The confirmation covers the pressed row's own actions.** The panel was anchored below the actions cell (`top-full`), so it sat exactly over the next row and read as a question about that claim. It is now laid over the pressed row's own actions cell (`absolute inset-y-0 right-0`), covering that row's two buttons; row height and table width unchanged. The test asserts the placement classes and that the panel sits inside the pressed row's cell.
2. **A live run's fired rules show without a reload.** On run `2bd08a61`, watched live to *Awaiting human review*, the run page showed no *Why it went to a person* until it was reloaded. Cause: `useRunStream` refetched the run and audit queries only on each `agent_completed` event, and the backend writes the `escalation_decision` and terminal rows after the Guardrail's completion (the live escalation event is emitted before its row), so the rows the page held were the ones read before the decision was written; the run query, which 404s while the run is in flight and does not retry, was never asked again; and `deriveFiredRules` read rows and the run record only, never the live event. Fix, in two parts in keeping with Prompt 29's rule that the rows are read first and the stream speaks where they are silent: the terminal event now invalidates `['run', cid]` and `['audit', cid]` as well as the claim and the claims list, so the finished record is re-read the moment it is complete; and `deriveFiredRules(rows, events, run)` reads the live `escalation_decision` event's `fired_rules` (`PipelineEvent.fired_rules`, additive to the frontend type — the backend's `EscalationDecisionEvent` has always carried it) when no row has them, so the line appears the instant the event arrives and the record follows. `hooks/useRunStream.test.tsx` is new (the hook's first test): the invalidations at an agent's completion, at the terminal event, and a malformed frame ignored.

## Findings and deviations from the plan

- **Two changes at the gate** (register R-26): one confirmation open at a time and a click outside closes it (the plan had Escape and the two buttons); the refusal sentence names the claim number, not the id, which the pipeline endpoints could give for free once they loaded the record for the 404.
- **Two defects found by the verification and fixed before close-out** (above): the panel's placement, and the fired rules missing after a live run. The second was latent since Prompt 29: the rules were only ever read from the rows or the run record, and nothing re-read either when the run finished. Prompt 29's verification watched a live abort and a live settlement, neither of which has fired rules, so it did not show.
- **One mutation test, not two.** The plan predicted the disabled-button mutation would fail two tests; one test covers both decisions, so it fails one.
- **Test counts under the prediction.** Backend 540 against "about 545", frontend 206 against "about 210": the plan's list was written per case and several cases share a test.
- **`uv.lock` carried the old project version again** after the `pyproject.toml` bump, as after Prompt 30; synced in `a4c780b`, which is the commit the deployed image was built from (the workflow diffs the backend paths, and the lockfile is one).
- **Two findings from the verification, recorded in the backlog, not built:** on run `2bd08a61` the Adjuster recommended $950,000 on an $850,000 claim, and nothing caps a recommendation at the reported amount; the Integrations activity feed shows times without dates, so calls from different days read as one day.
- **The Azure database** holds 32 claims at the close (31 on 14 November; the fresh Northwood claim `CLM-2026-5855FB8E` is Dermot's), three of them decided (`2FFB0434` approved, `75AFB337` and `5855FB8E` rejected), with new runs `2bd08a61`, `f23ea4dc`, `b3e7dc6c` and the step 6 runs; nothing was altered or removed.
