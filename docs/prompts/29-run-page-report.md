## What was built

**The derivation** (`frontend/src/pages/runDerivation.ts`, new, pure). Dermot's three findings of 10 November had one cause: the run page took every card's state from the live event stream alone, so a run opened afterwards showed four *queued* cards under a header that said *settled*, and an abort left the failing card *running* for ever. The page now reads the audit rows first and the stream only where the rows are silent. `deriveCards` gives one state per agent: an agent's own row means *done*, with its sentence from the row and its duration from the difference between consecutive rows' `created_at` (D2; the live event's `duration_ms` while the run is live); the `pipeline_aborted` row means the named agent *Failed*, with the reason in words and the sanitised `error_message` beneath, and every later agent *Not run* — the abort is applied before the agent's own row because a model-call failure writes both; a `pipeline_awaiting_human` row with `reason: guardrail_threw` means the Guardrail *Failed* in its own words. Where no row exists, `agent_started` means *running* and otherwise the card says *Waiting*. The live `pipeline_aborted` event goes through the same function, so an abort watched live moves the cards at the moment of the banner. `deriveAbort`, `deriveVariant`, `deriveStatus`, `deriveFiredRules` and (from the fixes) `deriveClaimId` read the header's facts by the same rule: the row, else the event, else the reconstructed run.

**The cards** (`components/AgentCard.tsx`). `AgentCard` takes a `state: CardState {status, summary, detail?, durationMs?, durationFromAudit?}`; `AgentStatus` gains `not_run` (∅), and the Guardrail's own failed verdict is ⚠ `escalated`, distinct from ✗ `failed` for an agent that broke (D4). Durations read "3.4 s" (`formatSeconds`), with a title saying "from the audit trail" when computed from the rows. A refused objection gives its reason in words ("those words do not name a policy provision"); the code stays in the audit trail. The ⓘ beside *Refused objections* (12 November) opens Dermot's explanation of what the line is and why the objections did not count; `Tooltip` gained an optional `label` for its button so a tooltip on a line of text is named for what it explains.

**The sentences** (`copy/run.ts`, new; `copy/labels.ts`, `copy/format.ts` extended). "Summarised the claim (Water damage)"; "Covered (92% confident)"; "Recommends $82,500 (85% confident)"; "Recommends $1,400,000 from the fixed demonstration file, no model call (82% confident)"; "Passed" or "Passed; 3 objections refused"; "Failed: cited policy wording the policy does not contain"; "Not run: the run stopped at the Adjuster"; "Failed: the Adjuster has no market range for the claim type Smoke damage" (`failureReason` reads the claim type out of the market-lookup message; `LLMProviderError` reads "the model provider refused or failed the call"; anything else "the {Agent} raised {error_type}"). The rule lines under the header quote the thresholds from `RULE_THRESHOLDS`, which `run.test.ts` asserts against `backend/app/escalation/policy.yaml` read from disk (D3): "Settlement over the $250,000 ceiling: $820,000"; "Validator confidence below the 65% floor (58% confident)". `labels.ts` gains `variantLabel`, `refusalReason`, `guardrailFinding`; `format.ts` gains `formatSeconds` and `formatPercent`.

**The header and notices** (`pages/RunDetailPage.tsx`). The first line names the claim (12 November): the claimant's name as a link to the claim page, then "Water damage · $85,000 · claim CLM-2026-9BB57A86"; the claim id comes from the run's own record and from the address only once the record has been read and names none, so a hand-edited address never fetches the wrong claim (`useClaim` gained an `enabled` flag for this); a claim that cannot be loaded says so. Then the variant as a sentence ("Standard run", "Strict Validator run", "Mistral run"; the stored name was shown in small type beside it until 12 November and is now left to the audit trail) and the outcome badge through `statusLabel`; the copyable id with its links; and *Why it went to a person* with one line per fired rule, from the `escalation_decision` row or the reconstructed run. "Run not found." appears when the page was not reached from the Claims page trigger — which now navigates with `state: { started: true }` — and both queries 404 (D5); the awaiting hint only for a run started here. While the run and audit queries are in flight and the stream is silent the page says "Loading this run…" in place of the cards (11 November): the deployed backend wakes from zero replicas in about half a minute, and four *Waiting* cards for that long read as the fault this prompt fixed. The abort banner reads "Run aborted: {reason}" from the row or the event.

**The waking notice** (`components/WakingNotice.tsx`, `copy/notices.ts`, 12 November). One shared component for every page that loads from the backend: once a request has waited more than three seconds it says "Waking the server. After a quiet period this takes up to half a minute." and goes when the data arrives or the request fails. Mounted beside the spinner on the Claims, claim (and its review panel), run, Audit, Policy, Integrations and compare pages, and on the Agents test bench while a call runs.

**Types, Guide, documents.** `api/types.ts` `PipelineResult` gains `doc_parser_output` and `validator_output`, which the API has returned since Phase 4. The Guide's *Try it* step 3 and *Reading a run page* are reworded for the sentences and the badge; `docs/walkthrough.md`'s two *Screen* lines read as the badge now reads. `CLAUDE.md` carries the status at each of the seven commits.

## Findings and deviations from the plan

- **Plan §7 steps 3 and 4 were not run.** They write to the Azure audit trail (a Harborline claim run live to a settlement and reloaded; a background claim of an unsupported type run live to an abort) and were left for Dermot's session. The live abort path is covered by the test *moves the failing card to Failed and the later card to Not run at once* and the reload path by the three after-the-event page tests, but neither has been watched on the deployed page. They remain the first thing to do when a run is next started on Azure.
- Part 3 deferred at the gate (D1) and the queue reordered the same day: register R-23.
- `ruleLine` and `failureReason` live in `copy/run.ts` with the other sentences, not in `labels.ts` as the plan's table had them; `labels.ts` gained the three value maps as planned. `formatPercent` was added for the bracketed confidence.
- The run page's notices, cards, claim line and id line became small components and its run-error subscription a hook, to keep every function under 50 lines; the plan had expected `CardSummary` inside `AgentCard` instead.
- `run.test.ts` references Node's types with a directive in that one file, because it reads `policy.yaml` from disk; `@types/node` was already a devDependency, so nothing was added. `readFileSync(new URL(…, import.meta.url))` fails under jsdom ("The URL must be of scheme file"), so the test resolves the path with `__dirname`.
- `formatSeconds(27950)` gives "27.9 s" because of binary floating point; the test example was changed to 27900. The function is unchanged: one decimal is the whole of the precision shown.
- Running Prettier over `src` reformatted eight untouched files that already fail `prettier --check` on `main`; they were reverted before the commit, so that tidy-up stays a separate decision.
- The hint "Awaiting pipeline_started…" is unchanged: the prompt did not name it.
- The waking notice on the Agents test bench shows after three seconds of any call, including a warm model call that simply takes longer; Dermot named the page, so it is there, and the wording is a reasonable guess at the cause on a page a visitor has just opened.
- The claim line uses the house apostrophe (’) in "Guardrail’s", as every other sentence in `copy/` does; the wording is otherwise Dermot's verbatim.
